# Ansible Agents Best Practices & Security Guidelines

This document outlines the standard operating procedures and security measures for Ansible agents operating within our Proxmox/Linux cluster environment.

## 1. Security First

### Principle of Least Privilege
- **Agents:** Should run with the minimum necessary permissions.
- **Sudo:** Use `become: yes` only for tasks that require root privileges. Avoid running playbooks as root directly.
- **Users:** Create dedicated Ansible users on target hosts with restricted sudo rules if possible (e.g., only specific commands).

### Secure Communication (SSH)
- **Keys:** Use SSH key-based authentication ONLY. Password authentication should be disabled for the Ansible user.
- **Passphrases:** Protect SSH keys with passphrases. Use `ssh-agent` locally to manage them.
- **Host Key Checking:** maintain `host_key_checking = True` in `ansible.cfg`. Do not disable this in production to prevent Man-in-the-Middle (MITM) attacks.

### Secrets Management (Ansible Vault)
- **NEVER** commit secrets (passwords, API keys, private keys) to version control in plain text.
- Use **Ansible Vault** to encrypt sensitive data.
- Store `vault_password_file` outside of the repository or use a password manager integration.
- Structure: Keep sensitive variables in `group_vars/all/vault.yml` or `host_vars/<host>/vault.yml`.

## 2. Inventory Management

### Structure
- Use a dynamic inventory if possible (especially with Proxmox), or a well-structured static inventory (`hosts.ini` or `hosts.yml`).
- Group hosts logically (e.g., `[proxmox_nodes]`, `[linux_guests]`, `[web_servers]`).

### Variable Precedence
- Understand Ansible variable precedence: `extra vars` > `playbook vars` > `inventory vars` > `group_vars` > `role defaults`.
- Use `group_vars` and `host_vars` for environment-specific configuration.

## 3. Playbook Development

### Idempotency
- Ensure all tasks are **idempotent**. Running a playbook multiple times should not change the state if the system is already configured correctly.
- Use `changed_when` and `failed_when` clauses to correctly report task status.

### Modularity (Roles)
- Break down complex playbooks into **Roles**.
- Follow the standard role structure: `tasks`, `handlers`, `templates`, `files`, `vars`, `defaults`.
- Reuse community roles (Ansible Galaxy) carefully; review them for security before use.

### Error Handling
- Use `block`, `rescue`, and `always` for error handling and cleanup.
- Ensure critical failures stop execution to prevent inconsistent states.

## 4. Proxmox Specifics

### Proxmox API
- Use the `community.general.proxmox` or `community.general.proxmox_kvm` modules for VM management.
- Create a dedicated API user/token in Proxmox with limited permissions for the Ansible agent.
- Do NOT use the root user for Proxmox API interactions.

### Guest Configuration
- Use `cloud-init` for initial VM provisioning (IP, user, SSH keys).
- Ansible takes over after the basic network connectivity is established.

## 5. Maintenance & Version Control

- **Git:** All playbooks and roles must be version-controlled.
- **Linting:** Use `ansible-lint` to enforce style and catch common errors.
- **Testing:** Test changes in a staging environment (staging VMs in Proxmox) before applying to production.

#### Configuration Steps:

    ```bash
    bw config server https://vaultwarden.nanunana.page/
    ```
2.  **Login:**
    ```bash
    bw login
    export BW_SESSION="<session_key_from_login>"
    ```

- It is highly recommended to use the `community.general.bitwarden` lookup plugin to fetch secrets dynamically.
- **Prerequisite:** `bw` CLI tool must be installed and logged in on the Ansible control node.

#### Example Usage:
```yaml
vars:
  proxmox_password: "{{ lookup('community.general.bitwarden', 'proxmox_api_user', field='password') }}"
```
- This avoids storing encrypted files in the repo entirely, effectively stateless secret management.
